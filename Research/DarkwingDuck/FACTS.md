## HUD-слой: геометрия из ROM-захватов (смена 29, proven)

Источник: `reference/gold_hurt_a41/oam_frames.bin` (240 к) + `gold_contact/oam_frames.bin`
(400 к) — реальный OAM после DMA; корреляция с `ram_frames.bin`. Харт-писатель читает тайлы
из таблицы в композиции спрайт-буфера, поэтому значения ниже — наблюдение, а не вывод из
`LDA #$82` в дизасме (те `#$82` — это записи состояния слота `STA $04D0,X`).

- **Скрытый маркер OAM #0 = `F8, C0, 00, 10`** — идентичен на всех кадрах обоих захватов и
  совпадает с портом (`HudComposer.oam[0]`). ФАКТ.
- **Метаспрайт сердца = 4 OAM-записи** (оба захвата, стабильная геометрия):
  - TL: Y=`$14`, X=`$10`, tile=`$80`, attr=`$00`
  - TR: Y=`$14`, X=`$18`, tile=`$80`, attr=`$40` (h-flip)
  - BL: Y=`$1c`, X=`$10`, tile=`$81`, attr=`$00`
  - BR: Y=`$1c`, X=`$18`, tile=`$81`, attr=`$40`
  ФАКТ (геометрия + тайлы полного сердца).
- **Вариант повреждения:** в `gold_hurt_a41` верхне-ПРАВая запись TR даёт tile=`$82`
  (set наблюдаемых тайлов сердца {80,81,82}); в `gold_contact` (удар ниже порога) только
  {80,81}. Интерпретация «$82 = трещина/потеря единицы» — ГИПОТЕЗА, нужен харт-таблица из
  сборки спрайт-буфера (банк 4/5), триггер по здоровью не подтверждён захватом.
- **Метаспрайт энерг.шкалы = 4 OAM-записи:** ряды Y=`$2c`/`$34`, X=`$10`/`$18`, tile=`$00`
  (пусто/прозрачно) в ОБОИХ захватах. Зажжённые пипсы (тайлы `$A0–$AB` из прежней записи)
  в этих захватах НЕ проявлены → правило пипсов НЕ верифицировано.
- **Индекс OAM у HUD НЕ фиксирован:** сердце всплывает на слотах `#0a…#0e` и чередуется по
  чётности кадра — т.е. ROM композитит HUD ПОСЛЕ переменной группы спрайтов (игрок/объекты).
  ФАКТ. Следствие: жёсткая раскладка порта в `HudComposer` на записях e1–e8 структурно неверна —
  это конкретная первопричина плато OamVerify (~101/256, рассогласование HUD-блока), а НЕ
  геометрия тайлов. Числа тайлов сердца/маркера в порту корректны.

## Сервис палитры `$EFBE` (банк 7) + модель `$0320 → $0300 → $3F00` (смена 41)

- **ТРИ СОСТОЯНИЯ, РАЗВЕДЁННЫЕ ПО ВРЕМЕНИ (ПОДТВЕРЖДЕНО 8 ЗАХВАТАМИ).**
  `$0320-$033F` — источник без фейда, `$0300-$031F` — рабочая копия (её пишут фейд `$C270`,
  загрузчики `$C2F9/$C319` и патчер `$EFBE`), `$3F00` — PPU-зеркало, которое загружает только NMI
  `$C059` (`LDA $18 / BEQ $C086 / LDX #$00 / STX $18 / 32 байта из $0300`). Отсюда
  **правило запаздывания `$3F00[f] == $0300[f-1]`**, измеренное напрямую: 2477/2499 (m1),
  1499/1499 (m2), 1466/1499 (m3), 1488/1499 (m4), 1477/1499 (m5), 1466/1499 (m6), 1499/1499 (m7),
  399/399 (door). Нарушения — только внутри окон загрузчика/смерти, где ROM пишет PPU напрямую.
- **ВТОРОЕ ПРАВИЛО, ВЫВЕДЕНО ИЗ ROM-ДАННЫХ (`Temp/pal_rule.js`):** каждый кадр, в котором
  `$0300` изменился, оставляет `$18 ≠ 0` в конце этого же кадра. 757 «кадров изменения» по 8
  захватам, **11 исключений**, и все 11 — кадры загрузки секции/смерти, меняющие индекс 1
  (m1 f814/f1983, m3 f50/f472/f894, m4 f190, m5 f499/f1278, m6 f322/f678/f1259). Обратно не
  работает: кадров с `$18 ≠ 0` без изменения `$0300` много (m2 1499, m4 1314, m7 838, m5 627) —
  это избыточные загрузки, они безвредны.
- **`$EFBE` РАЗОБРАН ПОБАЙТОВО И ПЕРЕНЕСЁН.** Вход: `LDA $3D / BPL $F007` — вооружён только
  при бите 7 в `$3D`; `base = $3D & $7F`. Дальше два счётчика: `LDA $3E / INC $3E / CMP $F04A,Y`
  (период) — при несовпадении RTS, `$3E` остаётся `старое+1`; при совпадении `STX $3E` (X=0) и
  `LDA $3F / INC $3F / CMP $F049,Y` (число шагов) — `$3F` обнуляется, когда старое `$3F == шагов`.
  Затем `CLC / ADC #$02 / ADC $00 / TAY / LDX $F049,Y` даёт смещение записи, и цикл
  `[индекс, v0, v1, v2]` пишет `STA $0300,Y` (никогда `$0320`), терминатор `BMI $F005` по значению
  ≥ `$80` вызывает `STA $18`. Нюанс 6502: `INC` меняет только память, поэтому `CMP`/`ADC` видят
  аккумулятор ДО инкремента.
- **ТАБЛИЦЫ (банк 7):** `$F008` — группы `[idx,v0,v1,v2,ff]` (`0d 16 11 01 ff | 0d 05 11 01 ff |
  0d 0f 11 01 ff | …`); заголовок `$F049` = `05 08 00 05 0a 0f 14 19 01 10 1e 23 02 02 28 2d 32
  01 06 37 3c ff ff`; колонка `$3D` — `$E5BD`. Расшифровка по миссиям: m1 base 0 (период 8, 5
  шагов, правит `$030D-$030F` значениями 16/05/0F/05/16/26 — это и есть цикл `$0300[13]`),
  m3 base 8 (1 шаг, период `$10`), m5 base `$0C` (2 шага, период 2, смещения `$28,$2D,$32`,
  вращает `$0305-$0307` как `1c,02,30 / 02,30,1c / 30,1c,02`).
- **СЧЁТЧИКИ — ЗАХВАЧЕННОЕ СОСТОЯНИЕ, А НЕ ВЫВОДНОЕ.** `$95` пишут сами кадровые движки

## Смена 43.2 (2026-10-16): `$E63C` выведен по дизасму целиком — у порта правило уже верное

  `$E63C` из `$DC14` (`flat_bank7.txt:3451`) и из `$DC67` (`:3495`). Выбор пути: `$DC03 TAY /

    STX $19` сливает очередь `$0360…` в `$2006/$2007` до записи с признаком знака и делает
    `RTS` в `$C139`. Ветка `$E7AF INC $19` и `$E7B1/$E7B3 LDA $FC / STA $28` внутри окна НЕ
    выполняется ⇒ `$28` остаётся `$00` (его и обнуляет `$DE3E`) — независимое подтверждение, что
    `StageSectionPass` не должен трогать `LastRedrawScroll`.
15. **NMI внутри окна — это `$C0A1`, а не рендер.** `$C006 LDA $F0 / ORA $9A / BEQ $C00F /
    JMP $C0A1`: только `INC $92`, четыре таймер-слота `$80/$81…` (шаг `$04`), APU-банк
    (`$F5/$F6` → `$FFF0`) и очередь банк-задач (`$DC,X → JSR $8003`). Путь `$C00F…`
    (PPU-регистры, OAM, `INC $95`) не выполняется ⇒ внутри окна `$95`/паритность кадров (G41)
    не двигается.
16. **Природа «бюджета проходов за кадр»:** число шагов `$25` между кадрами = сколько итераций
    `$DE86…$DE91` успевает выполнить CPU. Стоимость итерации = фиксированная часть
    (`$DE86…$DE91` + `$E698` + тело `$E69A…$E7A1`) + длина слияния `$C115`, зависящая от объёма
    записей, поставленных ЭТИМ проходом, то есть от данных колонки. Отсюда 9–17 проходов/кадр и
    короткий только ПЕРВЫЙ кадр окна: m5 `10,15,15,15,15,15,15,15,10`, m4
    `12,15,16,15,16,16,15,16`. Выведено из дизасма + `STR`-замеров, а не подогнано.
17. **Версия смены 54.4 опровергнута** (ранние выходы тела `$E698` по `$E954…$E965`/`$E99A`):
    в стиджинге `$05 = 1`, поэтому `DEC $05 / BEQ $E7A8` срабатывает на первом витке и ветвление
    по опкодам внутри тела не может ни добавить, ни убрать шаг `$25`; за проход `$25` всегда
    `+ $E7BE,X` (`$E78A…$E790`), а `$23` шагает ровно когда `$25 & $7F == $E7BF,X`
    (`$E794…$E79F`). Разница-port остаётся только тайминговой.
18. **Наблюдаемость харнесса (замеры):** `AgentScripts/PhysCompare.cs` сравнивает 20 полей и
    печатает покадровые `STR f<n> 25=порт/ROM 23=… 2F=… 1F=… 20=… 28=… FC=… 10=… 50=… 97=…`
    при любом изменении стримерных байтов; `$1F` сиится из захвата (пишет только `$E66C`),
    поэтому фантомных `1F passes:f1` больше нет (`grep -c` = 0). Артефакты:

    `25=7F/82 23=6E/6F`, оба `88` на f201), `Temp/m5_route_trace.txt` (f499 `0F/0B` … f507

19. **Приёмка не ослаблена:** `RESULT` 25/25 строк побайтово равен базе смены 45.2, кроме m6,
    где первый плохой кадр сместился f2→f330 — это закоммиченное закрытие G51 (смена 52).
20. **Стоимость одной итерации `$DE86…$DE91` посчитана по дизасму (G62, часть 1).**
    Фиксированная часть: `$DE86…$DE91` = LDA 2 + STA 3 + JSR 6 + LDA 3 + CMP 3 + BNE 3 = 20;
    `$E698 LDY #$00` = 2; заголовок прохода `$E69A…$E6FB` (вычисление `$24`, 5 записей адреса,
    4 счётчика `#$01`, терминатор) ≈ 105; копир-петля `$E70B…$E72A` выполняется **ровно 4
    витка** всегда (`X` = 0 или 2, шаг 4, выход при `CPX #$10`) = 4×41−1 ≈ 163; блок маски
    `$E742…$E763` ≈ 40; хвост `$E766…$E790` ≈ 25; `$E792…$E7A1` ≈ 12; выход `$E7A1 DEC $05`
    5 + `BEQ` 2 + `LDA $F0` 3 + `BEQ` 2 + `JMP $C115` 3 + `LDX/STX $19` 4 = 19.
    Переменная часть: `JSR $EB27` (`$E705`) и `JSR $EA36` (`$E708`) — декод комнаты/колонки,
    витки зависят от данных; `$E730 CMP #$38 / BCC $E742` добавляет 3-витковый перенос
    `$E738…$E740` (~27); и длина слияния `$C115…$C137` = Σ по записям (16 цикл/байт + 13 на
    заголовок). Итого ~1783 цикл/проход, что совпадает с ранее измеренным числом.
21. **Но статически предсказать batch всё равно нельзя.** Разрез окна по кадрам зависит от
    позиции счётчика циклов **в момент входа в `$DE24`** (насколько далеко главный цикл уже
    прошёл, когда сработал `$E388`/смерть-релоад), а это свойство пути, а не ROM-константа.
    То есть G62 снимается только циклом-точным CPU — а это прямой запрет AGENTS.md
    («эмулятор/ROM-исполнение внутри Unity не считается портом»). Вывод: `StagePassesPerFrame`
    остаётся приближением фиксированной скорости, а фазовый сдвиг `$23` на 1…2 кадра **внутри
    окна загрузки** — документированный остаток, а не блокиратор миссий.
