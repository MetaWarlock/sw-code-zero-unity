# Darkwing Duck NES → Unity: техническое задание для GLM-5.3-Flash / ZCode

Дата: 11 октября 2026. Рабочий каталог: `D:\Art\SW Code Zero Unity`.
Исходник: `Art/Darkwing Duck (USA).nes`.

## 1. Результат и границы задачи

Создать полноценный нативный перенос оригинальной американской NES-игры Darkwing Duck в существующий Unity-проект. Восстановить графику, уровни, анимации, музыку, звуки, интерфейс, последовательность экранов и игровую логику. Сохранить поведение оригинала при одинаковом вводе, включая особенности, которые влияют на прохождение.

Итог — редактируемый проект с понятной игровой логикой на C# и запускаемая Windows x64 сборка. Оригинальный ROM используется для исследования и воспроизводимого извлечения данных. Финальная игра использует извлечённые ресурсы и перенесённую логику; её запуск не требует установленного эмулятора, Python, ZCode, исследовательского каталога или обращения к исходному пути ROM.

Эмулятор нужен как эталон и лаборатория. Его запуск внутри Unity с выводом готового NES framebuffer не считается выполненным переносом. Статически перекомпилированная игра с аппаратным NES runtime также не заменяет конечную архитектуру. Такие решения допустимы как временные исследовательские адаптеры с явным статусом и планом удаления из игрового runtime. Отдельный APU-синтезатор для точного звука допустим: он не должен выполнять игровую логику ROM.

Не делать ремейк «по мотивам». Не менять уровни, баланс, физику, шрифты, разрешение, скорость, поведение врагов, количество объектов, правила выпадения предметов. Не добавлять сглаживание движения, новые способности, автосохранения и современные улучшения управления в режим оригинала. Диагностические возможности отделить от обычной игры.

Полнота включает:

- вступление, заставку, диалоги, выбор миссии, подтверждения, переходы;
- все семь основных уровней, все комнаты и переходы, секреты и бонусные участки;
- всех боссов и их фазы, обычных врагов, создаваемые ими объекты и снаряды;
- движение, прыжок, приседание, плащ, захват и отпускание уступов/крюков, специальные газы;
- здоровье, урон, неуязвимость, очки, жизни, предметы, смерть, контрольные точки, продолжение;
- HUD, паузу и экран состояния, завершение миссий, финал и титры;
- музыку, SFX, джинглы, переходы, прерывания и совместную работу звуковых каналов.

Установка и настройка ПО, написание экстракторов, реверс, реализация, тестирование и сборка — задачи исполнителя GLM/ZCode. Этот документ является заданием, а не заявлением о готовности игры.

## 2. Как работать в /goal и экономить ресурс

Прочитать этот документ целиком, затем `RESEARCH_HANDOFF_RU.md`. Составить очередь небольших зависимых задач. Сначала обеспечить измеримый вертикальный срез, затем расширять покрытие до всей игры. Не писать сразу десятки приблизительных игровых классов.

Вести четыре компактных файла в `Research/DarkwingDuck/`:

1. `STATUS.md`: текущий этап, что уже доказано, конкретный следующий шаг, актуальные команды.
2. `FACTS.md`: установленный факт → адрес/трасса/эксперимент → степень уверенности.
3. `GAPS.md`: неизвестные форматы и расхождения; для каждого — следующий проверяемый эксперимент.
4. `COVERAGE.csv`: система/уровень/объект/сценарий → извлечён → реализован → сравнен → доказательство.

После каждой существенной итерации обновлять только изменившееся. Перед продолжением читать STATUS и нужный раздел, а не заново весь ROM, весь репозиторий и все логи. Большие трассы фильтровать скриптами; в контекст передавать первый участок расхождения и связанные процедуры.

Для каждого блока работы применять цикл: гипотеза → минимальный эксперимент в оригинале → запись результата → перенос → сравнение → исправление первого расхождения. Наличие компилирующегося кода не доказывает правильность.

Повторять уже прошедшие проверки только после затрагивающего их изменения. Не переустанавливать рабочий инструмент без конкретной причины. Если инструмент дважды не удаётся запустить по одной причине, записать проблему и перейти к документированному запасному пути. Это ограничение относится к борьбе с инструментом, а не к полноте игры.

Не тратить итерации на поиск «идеального готового порта», если имеющихся средств достаточно для текущего этапа. Не создавать универсальный эмулятор или универсальный редактор NES. Нужен перенос конкретной игры.

Не завершать /goal на прототипе, первом уровне, извлечённом атласе, воспроизведённой музыке или успешном запуске сцены. Не менять критерии готовности, чтобы существующая реализация им соответствовала. При реальной внешней блокировке указать точную причину, уже выполненные обходные попытки и необходимое действие пользователя; не объявлять успех.

## 4. Архитектура конечной реализации

Предлагаемое разделение:

| Слой | Назначение |
|---|---|
| `Darkwing.Core` | Детерминированное состояние игры, ввод, порядок обновления, движение, столкновения, объекты, миссии; без UnityEngine |
| `Darkwing.Data` | Извлечённые таблицы, уровни, палитры, метаспрайты, анимации, скрипты событий; устойчивые ID и происхождение данных |
| `Darkwing.Presentation` | Камера, точное представление фона/спрайтов/HUD, вывод в Unity |
| `Darkwing.Audio` | Перенесённый звуковой секвенсор, арбитраж каналов, синтез/вывод аудио |
| `Darkwing.Unity` | Жизненный цикл приложения, Input System, конфигурация окна, запуск сцены, связь слоёв |
| `Darkwing.Tests` | Чтение эталонных сценариев, сравнение, отчёты; не включать исследовательские зависимости в release |
| `Tools/DarkwingResearch` | Офлайн-извлечение и наблюдение оригинала |

Это рекомендуемые границы ответственности, а не требование создать по классу на строку таблицы. Начать с минимального набора файлов. Общие решения выделять после подтверждения повторения в оригинале.

Источник истины о состоянии — Core. Transform, Animator, Rigidbody2D и AudioSource не должны определять правила оригинала. Unity Animator и AnimationClip не использовать для независимого отсчёта игровых кадров. Визуальная анимация выбирается из состояния Core.

Игровой шаг принимает явно заданный снимок NES-кнопок и выдаёт новое состояние, события и данные представления. Сохраняемое состояние включает все влияющие на будущее значения: целую и дробную части координат, скорости, таймеры, флаги, RNG, порядок/занятость слотов, камеру, состояние миссии и звукового секвенсора. Сериализация должна иметь версию.

Хранить целочисленные/фиксированные значения оригинальной разрядности. Не предполагать заранее Q8.8: восстановить формат каждой величины. Проверять переполнение байтов, знаковость, переносы и порядок операций 6502. При переносе отдельных процедур сначала сохранять эквивалентность, затем улучшать имена и структуру под действующими проверками.

Не использовать Unity Physics2D как источник точной платформенной физики. Восстановить исходные пробники столкновений, порядок проверок и коррекции позиции. Tilemap может представлять геометрию, но не должен сам задавать семантику контактов.

## 5. Эталон и определение «1 в 1»

Эталон — предоставленный ROM, работающий в зафиксированной конфигурации проверенного NES-эмулятора. Для каждого набора эталонов сохранять ROM hash, версии/хэши инструментов, исходное состояние, настройки изображения/звука и последовательность ввода. Не сравнивать с роликами YouTube, фанатскими портами или случайным набором спрайтов.

Проверять отдельно:

- **логику:** точное совпадение наблюдаемых дискретных состояний и переходов на одинаковых шагах;
- **геометрию:** целые/дробные координаты, скорости, hitbox/probe, момент столкновения, камера;
- **изображение:** одинаковые исходные 256×240 кадры при согласованной палитре и фазе захвата;
- **звук:** последовательность событий/записей, время, арбитраж и итоговый сигнал;
- **полноту:** прохождение и покрытие всех игровых систем, включая ответвления и редкие состояния.

NES не хранит единственную «правильную RGB-палитру телевизора». Для измерений зафиксировать преобразование индексов цвета в RGB эталонного эмулятора. Не менять палитру между сравнениями. CRT-фильтры и растяжение до телевизионного соотношения сторон не входят в базовое сравнение.

Частота NTSC приблизительно 60.0988 Гц; её нельзя подменять 50 Гц Unity FixedUpdate или жёсткими 60 Гц и объявлять идентичность. Выбрать воспроизводимую модель времени и зафиксировать точное значение/рациональное представление используемого эталона. Для покадровых тестов шагать по счётчику, без зависимости от часов ПК. При интерактивном запуске использовать аккумулятор времени; изменение FPS окна не должно менять симуляцию.

Разделить PPU-кадр, NMI, завершённое обновление игровой логики и опрос контроллера. Если исходник пропускает игровые обновления под нагрузкой, воспроизвести подтверждённые задержки в соответствующих условиях. Не выводить их из скорости выполнения C# на ПК.

Перед использованием golden trace доказать воспроизводимость самого оригинала из одинакового snapshot. Зафиксировать состояние RNG и неизвестной RAM. Разные моменты запуска/опроса могут дать разные траектории даже при внешне одинаковых действиях.

Если найдено расхождение, искать первый отличающийся шаг, затем конкретное поле, затем процедуру. Не маскировать дрейф периодическим принудительным присваиванием эталонной позиции и не проигрывать готовую траекторию вместо симуляции.

## 6. Извлечение данных

Все преобразования выполнять воспроизводимыми скриптами с проверкой исходного hash. Каждый экспортированный ресурс получает ID, исходный диапазон/указатель, банк и версию экстрактора. Один CPU-адрес без банка недостаточен.

Не писать игровой код, читающий произвольные магические смещения ROM во время обычной игры. Исследовательские смещения преобразовать в именованные, проверяемые таблицы/ресурсы сборки.

### 6.1 Графика

Извлечь все CHR-тайлы как 2-битные индексы. Сохранить исходную банковую организацию и дубликаты с адресами. Отдельно восстановить привязку банков, фоновые/спрайтовые палитры, их изменения и состояния fade. Grayscale-превью из подготовительного скрипта — диагностические картинки, а не готовые цветные ассеты.

Разобрать метатайлы, макротайлы и экраны; сравнить собранное изображение с оригиналом. Извлечь композицию спрайтов: порядок частей, смещения относительно игрового origin, tile ID, атрибуты, отражения и приоритет. Не обрезать каждый кадр с новым pivot: origin персонажа должен оставаться устойчивым.

Не считать 8×8 тайл самостоятельным персонажем. Для каждой анимации восстановить длительность кадров, повторение, переходы и зависимость от состояния. Проверить, означает ли таймер N ровно N обновлений либо N+1; не угадывать.

Оригинальные шрифты, иконки HUD и текстовые карты перенести из ROM. Не заменять их системным шрифтом/TMP. Раскодировать строки и управляющие команды диалогов, разметку, скорость печати и пропуск.

### 6.2 Уровни и объекты

Сохранить исходные layout ID, размеры, массивы скролла/дверей, размещения объектов и связи между комнатами. Внутренний порядок банков не является порядком открытия миссий. Не соединять все непустые экраны в одну непрерывную геометрию без разбора переходов.

Восстановить типы поверхности и поведение контакта сверху/сбоку/снизу. Различать визуально одинаковые тайлы с разной семантикой. Отдельно обработать односторонние платформы, крюки/уступы, шипы, двери, движущиеся объекты и специальные поверхности, найденные в коде.

Каталог объектов строить по размещениям **и** по процедурам динамического создания. Одного списка стоящих на карте врагов недостаточно: там отсутствуют некоторые выпадающие предметы, снаряды, эффекты и дочерние части боссов.

Для каждого типа записать: источник параметров; функцию поведения; состояния и переходы; начальные значения; анимации; движение; hitbox/hurtbox; урон/HP; уязвимости; создаваемые объекты; условия спавна, удаления и повторного появления; звуки; RNG. Сохранять порядок слотов и обновления, если он влияет на поведение.

### 6.3 Звук

В ROM музыка преимущественно представлена программой и последовательностями команд для APU, а не готовыми WAV. Выгрузка CHR и запись одного прохождения не извлекают весь звук.

Найти init/update звукового движка, очередь команд, таблицы песен/SFX, данные каналов, инструменты/огибающие, темп, циклы и переходы. Проследить записи `$4000–$4013`, `$4015`, `$4017`; для DMC исследовать связанные данные и банки, если он используется. Отсутствие DMC в одном эксперименте не доказывает отсутствие во всей игре.

Составить полный каталог звуковых команд: ID, тип, источник данных, места вызова и проверенный сценарий. Отделить используемые, неиспользуемые и пока неизвестные записи. Для прослушивания экспортировать WAV с точным началом и описанием loop, но сохранить исходные последовательности как первичные данные.

Для итоговой точности предпочтителен перенос секвенсора и арбитража с проверенным APU-синтезом. Музыка и эффекты используют общие каналы: простое одновременное воспроизведение независимых WAV может давать неверный результат. Исследовать прерывание канала эффектом, возврат музыки, фазу, pause/resume, смерть, смену миссии и джинглы.

APU включает два pulse-канала, triangle, noise и DMC; смешивание нелинейное. Не заменять синтез синусоидой или случайным шумом. Допустимо использовать подходящую библиотеку синтеза с зафиксированной версией и лицензией. Аудиопоток Unity получает готовые сэмплы через ограниченный буфер; callback аудиопотока не должен обращаться к scene API, читать файлы и выполнять тяжёлые выделения памяти.

Для идентичного синтезатора и одинакового исходного состояния требовать совпадение PCM после единственного документированного выравнивания задержки. Если backend отличается, отдельно требовать точное совпадение управляющих событий и заранее установленный допуск сигнала, обосновав его ресэмплингом/фильтрацией. Нельзя подбирать допуск после появления ошибки. Музыка, извлечённая из стороннего NSF, не становится эталоном без проверки соответствия этому ROM.

## 7. Восстановление игровой логики

Начать с главного цикла, NMI, обработки ввода, выбора банков, состояния игры и порядка обновления. Использовать динамическую трассировку для отделения кода от данных и определения реальных целей косвенных переходов. Наличие дизассемблированного текста не означает, что управление потоком восстановлено.

При переносе процедуры фиксировать её контракт: входные поля/регистры, выходы, побочные эффекты, вызываемые процедуры, банки, допустимые состояния и разрядность. Сначала сравнивать на реально достижимых состояниях. Случайные данные добавлять только после определения инвариантов; произвольные байты RAM часто задают невозможную ситуацию.

### Игрок

Восстановить: движение и разворот; старт/продолжение/окончание прыжка; управление в воздухе; падение; приседание и стрельбу из него; плащ и правила отражения/блокировки; захват уступов и крюков; перемещение/прыжок из висения и отпускание; урон, отбрасывание, неуязвимость, смерть и возрождение.

Управление проверять в ROM. Руководство указывает A для прыжка и B для стрельбы, однако раздел про уступы содержит противоречивые обозначения кнопок. Источником реализации служит эксперимент, а не исправление документации по догадке.

Не добавлять coyote time, jump buffer и ускорение, если этого нет в оригинале. Проверить приоритет одновременных направлений, обработку held/pressed/released, автоповтор и поведение при паузе. Host-ввод преобразовывать в восемь NES-кнопок; тесты используют именно эти кнопки, независимо от раскладки клавиатуры.

### Оружие и бой

Обычный газ и три специальных типа: Heavy, Thunder, Arrow. Проверить правила подбора/замены адаптера, включения через Select, расход энергии, отсутствие энергии, предельное количество снарядов, интервалы выстрела, спавн относительно игрока, столкновения и время существования.

По руководству Heavy/Thunder расходуют по 2 единицы, Arrow — 3; эти значения должны быть подтверждены исходником или трассой. Восстановить ударные волны Heavy и применение Arrow как временной опоры. Для плаща составить таблицу взаимодействий с конкретными типами атак.

### Враги, боссы и прогресс

Боссов Moliarty, Quackerjack, Wolfduck, Liquidator, Megavolt, Bushroot и Steelbeak привязать к фактическим миссиям и внутренним ID. Для каждого восстановить фазы, таймеры, паттерны атак, HP, окна уязвимости, дочерние объекты и завершение боя. Не заменять их общей моделью «ходит и стреляет».

Для всех объектов проверять активацию относительно камеры, offscreen-логику, респавн после возврата, взаимодействие с ограниченным пулом. Отдельно восстановить RNG и число его вызовов: одинаковая формула с другим порядком вызовов даёт другую игру.

Прогресс включает набор доступных/пройденных миссий, события открытия следующих, переходы в финальную миссию, сохранение/сброс состояния при смерти и продолжении. Проверить все допустимые порядки выбора миссий по модели переходов; полное эталонное прохождение одного порядка дополнить сценариями альтернативного выбора.

## 8. Представление в Unity

Базовый кадр — 256×240. Структурный экран уровня 8×8 макротайлов по 32 px имеет размер 256×256: это не разрешение вывода. Его связь с видимой областью, HUD и вертикальным переходом измерить отдельно. Не отрезать последние 16 строк исходных данных.

Текстуры: Point, без mipmaps и компрессии; целочисленное увеличение; предсказуемые пиксельные pivots. Отключить MSAA, HDR, постобработку, динамическое разрешение и влияющее на цвет освещение для оригинального изображения. Использовать одну согласованную шкалу PPU, например 16; логика остаётся в NES-координатах, преобразование в Unity выполняет адаптер.

В существующем URP используется `UnityEngine.Rendering.Universal.PixelPerfectCamera`; не устанавливать отдельный Built-in пакет Pixel Perfect. Сначала проверить API установленной версии. Для первоначального строгого renderer допустим собственный составитель 256×240 из извлечённых тайлов/метаспрайтов и состояния Core с выводом текстуры Unity. Это допустимый способ представления нативной логики, а не запуск оригинального CPU. Если позже выбран SpriteRenderer/Tilemap, сохранить те же проверки изображения.

Linear color space уже активен. Не переключать его вслепую. Согласовать sRGB import, выбор render target, shader и момент readback; исключить двойную gamma-конверсию. Проверить палитру на конкретных RGB-значениях эталона.

NES-приоритет спрайтов не сводится к сортировке «перед фоном/за фоном». Важны порядок OAM, прозрачный индекс, приоритет выбранного пикселя и лимит спрайтов на строку. Исследовать мерцание, обрезку слева, изменения палитры/скролла внутри кадра и воспроизвести используемые игрой эффекты. Отключение лимита спрайтов не входит в точный режим.

Камеру обновлять по восстановленным правилам, без Cinemachine damping. Субпиксельная логика и целопиксельное отображение — разные вещи: не округлять хранимую позицию игрока при выводе. HUD и меню отрисовывать в той же сетке; диагностические панели можно выводить отдельно.

При неподходящем размере окна добавлять поля. Режим квадратных исходных пикселей использовать для приёмочных сравнений. Параметры окна/масштаба не должны менять число симуляционных шагов или координаты.

## 9. Последовательность исполнения и контрольные точки

Каждый этап заканчивается рабочим артефактом и доказательствами. Нельзя переходить к массовому переносу контента, пока фундаментальная ошибка в формате или времени не устранена.

### M0 — подготовка и воспроизводимость

**Сделать:** прочитать существующие материалы; проверить hash ROM и состояние проекта; обеспечить локальную историю изменений; выбрать доступный эталонный инструмент. Использовать уже имеющиеся инструменты после проверки, а не устанавливать весь список альтернатив. Подготовить единый способ запуска ограниченного сценария с вводом, snapshot, PNG, RAM и звуком.

**Выход:** `toolchain-lock.json`, описание конфигурации эталона, воспроизводимый сценарий запуска оригинала. Два одинаковых запуска из одного состояния дают одинаковые значимые данные. Если этого нет, исследовать причину до создания golden-тестов.

**Важно:** инструментальные пробы из подготовки задания не являются полной проверкой детерминизма. Начальные сессии записаны в разных фазах и предназначены для исследования.

### M1 — инвентаризация и извлечение

**Сделать:** проверить/доработать имеющийся экстрактор; построить manifest исходных диапазонов; извлечь графические индексы, композиции, карты, размещения, палитры, UI и таблицы анимации. Разрешить исключения RAM-кадров и специальных ссылок экранов. Зафиксировать ещё неразобранные диапазоны.

**Выход:** воспроизводимый экспорт с адресами, hash и проверками обратного кодирования там, где преобразование обратимо. Просмотрщик реально собранных ресурсов, пригодный для сопоставления с оригиналом. Для каждого заявленного ресурса понятно, откуда он получен.

**Условие:** нельзя объявить «все ассеты извлечены» после выгрузки CHR. Музыка, скрипты, динамические палитры/кадры, UI, временные объекты и неиспользуемые данные учитываются отдельно. Все байты ROM должны сохраняться в исходнике/дампе; смысловое назначение неизвестных диапазонов не выдумывать.

### M2 — модель времени и эталонный интерфейс

**Сделать:** восстановить главный цикл, опрос ввода, основные состояния RAM, порядок обновления, RNG и правила камеры. Определить единую фазу сопоставления. Реализовать минимальный Core со шагом, сбросом и snapshot; инфраструктуру ввода/вывода, сравнения и отчёт первого расхождения.

**Выход:** оригинал и Core принимают один формат сценариев. Подтверждены поля состояния и их привязка к RAM/коду. Повторение сценария в Core не зависит от host FPS. На этом этапе Core ещё может поддерживать только минимальную часть поведения — статус должен это отражать.

### M3 — точный вертикальный срез

**Сделать:** старт одного выбранного уровня, исходная комната, игрок, камера, основные поверхности, обычный выстрел, один обычный противник, получение урона, смерть/возрождение. Выбирать небольшой участок, покрывающий перечисленные взаимодействия, а не обязательно всю первую миссию.

**Выход:** набор коротких сценариев с покадровым сравнением координат, таймеров, состояний, коллизий, кадров анимации и изображения. Значения не подобраны на глаз; у параметров есть источник. После расхождения можно получить точный шаг и связанный участок кода.

**Условие:** до массового добавления врагов устранить проблемы точности этого среза. Не тратить время на красивое меню/редактор, пока игрок двигается неверно.

### M4 — полная механика игрока и общие системы

**Сделать:** завершить все состояния игрока, специальные газы, платформы/крюки, предметы, здоровье, очки, жизни, checkpoints, pause/continue и ограничения пулов объектов. Проверить пограничные случаи и комбинации состояний.

**Выход:** таблица механик с эталонными сценариями. Проверены последствия расхода энергии, столкновений на углу/границе экрана, поворота во время атаки, урона в прыжке/висении, смерти от разных причин.

### M5 — звуковая система

**Сделать:** восстановить каталог музыки/SFX, секвенсор, управление каналами, синтез и связь игровых событий со звуком. Работу по обнаружению движка можно начинать раньше; здесь требуется законченный перенос.

**Выход:** проверенная таблица команд, прослушиваемые экспорты, loop-метаданные, совместные сценарии music+SFX и сравнение с оригиналом. Пауза, смерть, переход и одновременные эффекты работают правильно. Нет накопительного рассогласования звука и игры.

### M6 — все уровни, враги и боссы

**Сделать:** переносить по миссии, с её объектами и боссом. Для каждой повторять один шаблон приёмки: геометрия → переходы → активация объектов → обычные враги → специальные события → босс → завершение → секреты/бонусы → регрессия общих систем.

**Выход каждой миссии:** проходимый путь от входа до выхода, набор сохраняемых эталонных состояний, покрытие всех размещённых и динамически создаваемых типов в этой миссии, сравнение ключевых сценариев. Сложные состояния боссов проверять по фазам, затем целым боем.

**Условие:** наличие геометрии семи уровней не равно готовности семи уровней. Не подменять неизвестные типы универсальным врагом или молчаливым пропуском. Runtime должен обнаруживать неизвестный ID и давать диагностическую ошибку в тестовом режиме.

### M7 — полный игровой маршрут

**Сделать:** вступление, диалоги, выбор/открытие миссий, HUD, пауза, game over, continue, переход к финалу, финальная сцена и титры. Восстановить сохранение/сброс состояния между этими экранами.

**Выход:** новый запуск → обычное полное прохождение → финал. Отдельные сценарии проверяют альтернативные порядки выбора, отказ/подтверждение миссии, пропуск текста, повтор после смерти и продолжение. Все строки, изображения и звуки берутся из восстановленных данных.

### M8 — завершение, сборка и доказательства

**Сделать:** выполнить полную приёмку; устранить расхождения; удалить исследовательские обходы из игрового runtime; собрать Windows x64; запустить сборку вне Editor. Проверить воспроизводимость сборки проекта и зависимости поставки.

**Выход:** `Builds/DarkwingDuck/` с приложением; инструкция управления и сборки; `ACCEPTANCE_REPORT.md`; актуальная матрица покрытия; список известных ограничений с честным статусом; notices используемых компонентов. Не выдавать запуск в Editor за проверку standalone.

## 10. Контракт эталонных сценариев

Формат сценария определить один раз и применять к оригиналу и переносу. Обязательные поля:

| Поле | Содержание |
|---|---|
| Идентификатор | Устойчивое имя сценария и проверяемая механика |
| Происхождение | Hash ROM, версии инструментов, версия схемы данных |
| Начало | Сброс или snapshot с hash; его способ получения |
| Фаза | Относительный шаг, PPU-кадр и выбранная граница обновления |
| Ввод | Полный набор восьми NES-кнопок; интервалы с явно определёнными включёнными границами |
| Длительность | Число шагов и конечное условие |
| Наблюдения | Поля состояния, события, кадры, аудио/записи APU |
| Проверки | Ожидаемый результат и заранее заданные допуски |
| Покрытие | Какие системы, состояния и переходы затронуты |

Не переносить `.mss` напрямую в C# как состояние игры. Нужен документированный преобразователь/фикстура известных полей либо достижение одинаковой точки из reset. Mesen snapshot содержит аппаратное состояние, которого в нативной модели может не быть.

Сравнивать семантические поля по карте соответствия. Полное равенство всей RAM не требуется от нативной архитектуры; оно полезно между запусками оригинала и при сравнении отдельно перенесённых низкоуровневых процедур. Не включать в hash нативного состояния случайный порядок словарей, адреса объектов или неинициализированное выравнивание структур.

Golden-данные неизменяемы для проверяемой реализации. Их обновление допускается только после доказанной ошибки в захвате/конфигурации, с объяснением и повторной записью из оригинала. Изображение самой Unity-реализации не может быть новым эталоном её же правильности.

Для каждого теста выводить PASS/FAIL, количество реально выполненных шагов, первое расхождение, ожидаемое/фактическое поле, пути к данным и command line. Для кадров сохранять эталон, результат и diff; для звука — исходные сигналы и сравнительный отчёт. Успешный exit code без необходимых файлов/шагов не считается успехом.

## 11. Матрица приёмки

| Область | Обязательное покрытие | Что должно совпасть |
|---|---|---|
| Ввод/время | held/edge, одновременные кнопки, pause, разные host FPS | порядок опроса и переходы на шагах |
| Игрок | все состояния и переходы, контакты с разных сторон | позиция с дробной частью, скорость, таймеры, флаги |
| Геометрия | все комнаты, особые ссылки, переходы, поверхности | расположение, правила контакта, камера |
| Оружие | четыре режима, энергия, лимиты, взаимодействия | спавн, траектории, срок жизни, расход и попадания |
| Противники | все используемые типы и существенные состояния | активация, движение, атаки, урон, удаление/респавн |
| Боссы | все семь, все фазы, дочерние объекты | паттерны, таймеры, HP, уязвимость и финал боя |
| Предметы/RNG | размещённые/выпадающие, секреты, переполнения счётчиков | тип, момент появления, эффект, RNG-последовательность |
| Прогресс | доступность миссий, смерть, continue, финал | переходы и сохраняемые поля |
| Графика | все типы экранов, палитры, HUD, приоритет, мигание | исходные 256×240 пиксели согласованного эталона |
| Звук | все команды и сочетания, циклы, переходы | события, каналы, время и согласованный сигнал |
| Приложение | Editor и standalone, потеря фокуса/возврат, масштаб | отсутствие влияния окружения на игровые правила |

Приёмочные сценарии должны включать обычное полное прохождение без изменения RAM, warp и принудительного уничтожения боссов. Snapshot/cheat допустимы для локальных экспериментов и покрытия редких состояний, но такой эксперимент помечается и не засчитывается как обычное прохождение. Записанный ввод может подаваться автоматически: он должен управлять настоящей симуляцией, а не воспроизводить видео.

На финальной приёмке:

1. Все обязательные строки матрицы имеют проверяемые доказательства, нет `TODO`, молчаливых заглушек и необработанных достижимых ID.
2. Пройден весь маршрут до финала в standalone; сценарий и артефакты сохранены.
3. Для детерминированных механик нет необъяснённых расхождений состояния по кадрам. Повторные прогоны воспроизводимы.
4. Графика проходит точное сравнение на зафиксированных сценариях; любые технические исключения имеют узкую причину и не скрывают отличия геймплея. Общий процент сходства картинки недостаточен.
5. Звуковая точность подтверждена по принятому в разделе 6.3 контракту, а не только субъективным прослушиванием.
6. Проект собирается по документированной процедуре. Release не загружает ROM для исполнения инструкций, не запускает Mesen и не зависит от исследовательских абсолютных путей.
7. Исходные данные сохранены; сборка содержит необходимые ресурсы; версии внешнего кода и происхождение ассетов документированы.

Это инженерный критерий готовности, а не математическое доказательство эквивалентности на всех возможных последовательностях ввода. В финальном отчёте указывать реально проверенное покрытие. Непроверенную систему нельзя объявлять идентичной.

## 12. Как решать типичные затруднения

| Симптом | Следующее действие |
|---|---|
| Неверно выглядят тайлы | Проверить CHR-bank, порядок битплоскостей/битов, палитру, порядок четвертей и прозрачный индекс |
| Спрайт смещается между кадрами | Сверить исходный origin, знаковые offsets, отражение и OAM Y; не лечить разными произвольными pivots |
| Первый кадр совпал, дальше дрейф | Проверить фазу захвата, held/edge input, субпиксели, порядок обновления и RNG |
| Игрок застревает на границе | Сравнить исходные collision probes и порядок коррекций, переносы между screen/local координатами |
| Уровень заканчивается неверно | Проверить layout/scroll/door как отдельные данные и внутренний ID комнаты |
| Отдельные кадры анимации мусорные | Проверить RAM-указатели и текущие CHR-bank/palette; не переводить любой указатель в ROM-offset |
| Ghidra показывает невозможный цикл | Проверить банковый контекст и переход после записи mapper; декомпилятор не доказывает поведение |
| Статический рекомпилятор собрал библиотеку | Это ещё не рабочая игра: проверить runner, конфигурацию конкретного ROM и fallback; не менять цель на оболочку |
| Музыка похожа, SFX звучат неверно | Проверить общий арбитраж каналов, порядок APU writes, фазу, envelope, возврат музыки |
| Сравнение «почти проходит» | Найти первое расхождение; не повышать tolerance, не замедлять оригинал и не отключать проблемный объект |
| Не найден готовый дизассемблированный код | Продолжать динамический реверс имеющегося ROM; внешний полный дизасм не является зависимостью проекта |

## 13. Первый рабочий пакет для исполнителя

Начать с M0, сверить сохранённые инструменты и материалы. Затем уточнить имеющийся экспорт M1: три RAM-кадра, специальную ссылку `0x98` финальной миссии, палитры/CHR-привязки и игровые значения метатайлов. После этого выбрать небольшую исходную комнату и построить M2–M3.

В конце первой итерации предоставить короткий отчёт: какие существующие материалы пригодны; какой эталонный сценарий воспроизводим; что установлено фактически; какое неизвестное исследуется следующим; где находятся результаты. Продолжать /goal согласно очереди, не запрашивая повторно разрешение на обычные локальные действия, входящие в задачу.
